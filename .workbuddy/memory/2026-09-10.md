## P3 · 细节打磨

逐文件审计后确认 4 项并全部修完（清单 #17–#20）。

### 关键发现：Tailwind v4 的 hover 在触摸端不生效
`hover:` 变体被实现为 `@media (hover: hover) { &:hover }`。手机 primary pointer 是 coarse → 媒体查询不命中 → **`group-hover:` 类在手机上完全不生效**。
因此 `MasonryTile` / `PreviewTile` 的图片说明浮层（标题+标签）在手机上一直不可见——原注释还写着"移动端常显"，注释与实现不符。
修法：浮层加 `pointer-coarse:opacity-100`（触摸常显），可悬停设备仍收在 hover。

### 其余三项
- **灯箱三态**：`status: loading/loaded/error`，加载中转圈、失败给「在新标签页打开」兜底；图片由 `opacity-0` 淡入。
- **动效降级**：图片 hover 位移/缩放改用 Tailwind 内置 `motion-safe:` 前缀（先试过自定义 `.tile-motion` 类 + CSS 覆盖，后觉得调用点自解释更重要而改掉）。
- **回到顶部**：新增 `src/components/ui/back-to-top.tsx`，挂 `App` 根节点；滚动 >900px 出现，`z-40` 低于弹层 `z-50`；自行判断 `prefers-reduced-motion` 决定 smooth/auto。

## P5 · 图片载荷调查（结论：**前端已到边界**，治本需开通托管方图片处理）

CLS 达标后转向真正在伤体验的 **LCP**。详细报告见 `UI-REFACTOR-PLAN.md` 第 15 节。

### 三次返工都在量法上（方法论教训）
1. **跨域资源字节数取不到**：`img.static.paiii.cn` 未返回 `Timing-Allow-Origin` → Resource Timing 的 `transferSize/encodedBodySize` **一律为 0**，首轮测出"图片合计 1 KB"的假数据。改用 Playwright `page.on('response')` 读原始 `content-length`，或落盘 `curl` + `wc -c`。
2. **不能用 dev server 测性能**：dev 下 Vite 不打包，87 个模块走限速连接 → **DCL 7 秒**，LCP 落到 index.html 的占位文字上。必须 `npm run build` + `vite preview`（DCL 回到 ~420 ms）。
3. **LCP 采集窗口要长于"下完整页"**：4G 下 9.3 MB ≈ 19 s。窗口 6 s 读出 6.3 s，窗口 26 s 读出 8.2 s —— 前者是截断假值。

### 实测结论
| 项 | 数据 |
|---|---|
| 图库首屏图片 | 24 张 **9.27 MB**（平均 395 KB，最大 1362 KB），占全站传输 72% |
| 原图真实尺寸 | 高至 `5760×3240` / `5000×2813`，而显示槽位仅 264px（桌面）/ 173px（手机）宽 |
| 4G LCP | 图库桌面 **8226 ms** / 手机 **10029 ms**（Poor 线 4 s）；首页手机 589 ms（健康） |
| LCP 元素 | 图库页是**后到达的随机大图**，不是第一张瓦片 → 单张优先级无效 |
| 首页懒加载 | 有效，首屏只拉 4 张 731 KB |

### 根因：托管方未开通图片处理
逐条实测 6 种主流语法（`imageMogr2/thumbnail/600x`、`!600x`、`/format/webp`、`/crop`、`imageView2/2/w/600`、`x-oss-process=image/resize,w_600`）→ **全部返回原图字节，md5 一致**。
响应头带 `EO-Cache-Status` / `EO-LOG-UUID` → 托管方是**腾讯云 EdgeOne**，源站路径 `imgtcpaiii/...` 形似同名 COS 桶。参数被当普通 query 透传 = 图片处理未开通。

### 收益量化（实测，非估算）

### 一个容易写错的直觉（已实测证伪）
**CSS multi-column 逐列向下填充，DOM 顺序 ≠ 视觉首屏顺序。** 桌面 4 列时 DOM `0,1,2,3,4` 全在第 1 列；首屏 15 张瓦片的起点索引是 `0,5,11,18`；手机 2 列首屏只有 `0,1,11,12`。
→ **"给前 N 张加 fetchpriority"是错的写法**，会把首屏外的图提前。

### 又一个测量假象：`grep -c $'\r'` 判行尾不可信

复核行尾时，`grep -c $'\r' 文件` 报告 index.html「100 行全是 CRLF」、index.css「564 行全是 CRLF」——**险些误判成"我的编辑污染了行尾"**。
用 Python 数字节复验：**工作区与 HEAD blob 全部是纯 LF，CR 字节数 = 0**；全仓库文本文件 **87 LF / 0 CRLF** + 1 个二进制 `public/og.png`。
交叉验证：`git diff --numstat` 显示 index.html 仅 11 行变更（正好是我新增的 preconnect 行）——**若真被整体翻转，改动量会等于整个文件行数**。

结论：`grep -c $'\r'` 在 `$(...)` + 嵌套引号下会假报警；**查行尾改用 Python 数字节或看 `git diff --numstat`**。已写入 `MEMORY.md`。脚本：`.workbuddy/shots/eol-census.py`。
